# BlockCheck2 для Zapret2

## 1. Назначение и область применения

BlockCheck2 — внутреннее дополнение CDPI UI. Оно подбирает стратегии Zapret2, объединяет их в один пресет, проверяет пресет и позволяет пользователю его редактировать. Дополнение делает больше, чем поиск отдельных работающих стратегий. После сканирования оно создаёт один мультипрофильный пресет, проверяет весь пресет и пытается заменить стратегию, которая вызывает конфликт.

Основной сценарий — сайты HTTP и HTTPS. Модель данных и каталог поддерживают QUIC, но стандартный UI скрывает параметр QUIC. Дополнение не подбирает стратегии для произвольного UDP-трафика приложений, например для голоса Discord. Обычный HTTP-запрос `curl` не может проверить такой трафик.

BlockCheck2 не является отдельным пакетом Магазина. Алгоритм находится в проекте `CDPIUI.AddOns`. UI и адаптеры CDPI UI находятся в проекте `CDPIUI`.

## 3. Последовательность сеанса

1. Пользователь выбирает один или несколько списков сайтов или создаёт «собственный список сайтов».
2. Для каждого списка пользователь выбирает один из двух режимов: список как единое целое или каждый сайт отдельно.
3. Пользователь выбирает быстрый, средний или полный режим.
4. На странице дополнительных параметров пользователь выбирает протоколы, версии IP, тайм-ауты, число запросов к каждой цели и параметр теста всех стратегий.
5. `BlockCheckSessionPreparationService` загружает встроенный каталог, разбирает входные данные и создаёт один `BlockCheckTarget` для каждой комбинации URL, протокола и версии IP.
6. Страница обзора параметров показывает консервативную максимальную длительность.
7. `BlockCheckAddOnService` выполняет предварительную проверку (preflight), базовую проверку (baseline), сканирование стратегий, синтез, проверку готового пресета и, возможно, его исправление.
8. `BlockCheckReportBuilder` создаёт отчёт. Он делает это также для результата best-effort и для отменённого сеанса с частичными данными.
9. Модель представления автоматически сохраняет отчёт JSON в историю.
10. Отдельное окно результата позволяет пользователю принять автоматический пресет или собрать пресет из всех доказательств.

## 4. Входные данные и цели

### 4.1. Домены и URL

`BlockCheckTargetInputParser` принимает:

- DNS-имя без схемы;
- абсолютный URL `http://` или `https://`;
- путь и строку запроса;
- нестандартный порт.

Парсер пропускает пустые строки и строки, которые начинаются с `#`. Он преобразует домены в IDN ASCII в нижнем регистре. Допустимы только DNS-имена. IP-литералы и другие схемы не могут быть целями.

Строка без схемы разворачивается во все выбранные протоколы. Явная схема ограничивает строку совместимыми протоколами. Каждая цель также разворачивается во все выбранные версии IP. Затем парсер удаляет дубликаты.

Один вызов парсера создаёт не более 200 целей (`BlockCheckTargetInputOptions.MaximumTargets`). Если входные данные дают больше целей, парсер возвращает `TARGET_INPUT_LIMIT_EXCEEDED`. Предел действует отдельно для прямого ввода и для каждого списка в режиме `WholeList`. В режиме `EachSite` парсер читает каждый домен отдельно.

ID вида `target-005-tls12-ipv4` — внутренний. UI показывает URL и данные подключения отдельно, например `https://example.org/path` и `TLS 1.2 · IPv4 · TCP:443`.

### 4.2. Списки сайтов

Доступны такие источники:

- списки, которые CDPI UI уже знает;
- локальные файлы TXT из диалога выбора файла;
- файлы TXT, которые пользователь перетаскивает на страницу;
- собственный список, который пользователь вводит в `CustomSiteListContentDialog`.

Загрузчик удаляет BOM и начальный `^` из каждой строки. Он пропускает пустые строки и комментарии `#`. UI не предлагает списки исключений как обычные входные списки.

У каждого списка один из двух режимов:

- `WholeList`: файл остаётся одной атомарной единицей. Итоговый профиль ссылается на файл через `--hostlist`.
- `EachSite`: загрузчик создаёт отдельный временный файл TXT для каждого домена. Так разные сайты одного списка могут получить разные стратегии.

Временные файлы имеют имена вида `site_0001_<hash>.txt`. Они находятся в `BlockCheck2/GeneratedSiteLists` в папке данных CDPI UI. Общее меню выбора списков их не показывает. Если подготовка или запуск завершается без отчёта, который пользователь может открыть, модель представления удаляет временные файлы. Если результат есть, файлы остаются, потому что на них может ссылаться отчёт или несохранённый пресет.

Собственный список находится в этой папке:

```text
Store/Items/LocalUserStorage/List/BlockCheck2/Custom
```

### 4.3. Атомарные списки

Один параметр `--hostlist` охватывает весь файл. Поэтому алгоритм не может разложить один список по нескольким конфликтующим профилям и ожидать, что каждый профиль обработает только «свои» домены.

`BlockCheckTargetGroupBuilder` объединяет в одну группу:

- проверки одного маршрута выполнения;
- все цели одного списка с одинаковой формой подключения;
- списки, у которых есть общие цели (транзитивно).

Строгая стратегия должна работать для всех целей группы. Сканирование, строгий оптимизатор, оптимизатор best-effort и `BlockCheckSynthesisService` используют одни и те же группы. Поэтому сайт списка, который проходит базовую проверку, остаётся в своей группе, и выбранная стратегия не должна его сломать.

Если разные домены одного атомарного списка проходят только с разными стратегиями, синтез добавляет предупреждение `NO_COMMON_SITE_LIST_STRATEGY`. Если после этого синтез не может создать профиль, проблема с тем же кодом становится ошибкой. Чтобы получить для сайтов разные стратегии, пользователь должен выбрать `EachSite`.

## 5. Протоколы и маршрут выполнения

В модели есть такие протоколы:

- `Http`: TCP, по умолчанию порт 80;
- `Tls12`: HTTPS с принудительными TLS 1.2 и HTTP/1.1;
- `Tls13`: HTTPS с принудительными TLS 1.3 и HTTP/1.1;
- `TlsAuto`: HTTPS без принудительной версии TLS и без ALPN;
- `Quic`: UDP и HTTP/3.

Маршрут выполнения определяет такой кортеж:

```text
host + IP version + transport + port + L7 protocol
```

TLS 1.2, TLS 1.3 и автоматический TLS одного домена могут дать отдельные строки доказательств. Обычный профиль Zapret2 не может выбрать действие по версии TLS после ClientHello. Поэтому выбор стратегии рассматривает совместимые проверки TLS одной формы как одно целое. Успех только на одной версии TLS считается частичным.

Версия IP — часть профиля. Модуль записи всегда добавляет `--filter-l3=ipv4` или `--filter-l3=ipv6`. Если браузер может использовать обе версии IP, включите в подбор обе версии. Успех `curl -4` не доказывает, что браузер, который использует IPv6, может открыть сайт.

## 6. Режимы запуска

`BlockCheckRunPresetFactory` задаёт параметры сканирования, синтеза и проверки пресета вместе.

| Параметр | Быстрый | Средний | Полный |
|---|---:|---:|---:|
| Рекомендуемое число запросов к каждой цели | 2 | 3 | 5 |
| Максимальный уровень каталога | Quick | Balanced | Exhaustive |
| Порог успеха | 100% | 80% | 80% |
| Разных успешных планов до ранней остановки | 2 | 2 | 4 |
| Ранняя остановка маршрута | Да | Да | Нет |
| Циклических запасных вариантов на профиль | До 1 | До 1 | До 2 |
| Циклический порог неудач (`fails`) | 2 | 3 | 3 |
| Максимум итераций исправления | 1 | 3 | 5 |
| Предпочтение оптимизатора | Скорость | Баланс | Стабильность |

Режим задаёт рекомендуемое число запросов. Затем пользователь может задать целое значение от 1 до 20. Значение применяется к:

- базовым проверкам;
- каждой паре стратегии и цели;
- минимальному числу попыток-доказательств в синтезе;
- проверке каждого кандидата готового пресета;
- оценке максимальной длительности.

Параметр «Не завершать после нахождения лучших стратегий» отключает раннюю остановку на быстром и среднем уровнях. Полный режим тестирует весь применимый каталог и без этого параметра. Параметр не расширяет выбранный уровень. Например, средний режим с этим параметром не тестирует стратегии Exhaustive.

## 8. Каталог стратегий

Исходный каталог — встроенный ресурс `strategy-catalog.v1.json`. `BuiltInStrategyCatalogExpander` добавляет стандартные семейства и задаёт версию каталога `2026.08.11-standard`.

Каталог содержит варианты HTTP, TLS и QUIC для таких семейств:

- `multisplit` и `multidisorder` с разными позициями;
- `fake` с `tcp_md5`, `badsum`, изменениями sequence, ack и timestamp, а также флагами TCP;
- `fakedsplit` и `fakeddisorder`;
- `hostfakesplit`;
- комбинации fake со split, faked или hostfake;
- QUIC fake и IP-фрагментация.

Каждый `StrategyDefinition` задаёт:

- стабильный `Id` и отображаемое имя;
- семейство и уровень сканирования;
- применимые протоколы и версии IP;
- базовую стоимость;
- поддержку circular;
- требования pre-host и входящего трафика;
- блобы;
- упорядоченные действия Lua, payload и диапазоны.

`StrategyCatalogValidator` отклоняет:

- неизвестные функции Lua;
- неизвестные фильтры payload;
- повторяющиеся ID;
- некорректные диапазоны;
- зарезервированные аргументы `strategy` и `final`;
- значения аргументов с небезопасными символами;
- источники блобов с абсолютным путём или `..`.

Регулярные выражения для ID, имён аргументов, значений аргументов и диапазонов заканчиваются на `\z`, а не на `$`. Поэтому значение с конечным переносом строки не проходит проверку. Порядок действий `--lua-desync` имеет значение, и модуль записи его сохраняет.

`CandidateNormalizer` создаёт сигнатуру фактического плана без отображаемых данных. Если у двух элементов каталога одинаковые действия, дополнение считает их одним техническим планом. Это относится к подсчёту успешных альтернатив и к выбору запасных вариантов.

## 9. Подготовка окружения

`CdpiuiZapret2StrategyRunner` запускает временные аргументы обычным путём: `ComponentTasksManager`, затем трей CDPI UI и ConPTY.

Перед базовой проверкой запускатель выполняет такие шаги:

1. Убеждается, что компонент Zapret2 и его исполняемый файл установлены.
2. Получает эксклюзивный семафор для компонента.
3. Записывает, какие из этих компонентов работают: Zapret2, Zapret Legacy, GoodbyeDPI, ByeDPI, SpoofDPI и NoDPI.
4. Останавливает компоненты, которые вызывают конфликт.

После сканирования или ошибки запускатель останавливает временный процесс. Затем он снова запускает компоненты, которые работали до этого. Очистка использует `CancellationToken.None`. Поэтому ручная отмена не останавливает восстановление окружения.

После каждого запуска стратегии запускатель ждёт `StartupGraceSeconds`. Если процесс завершается, предупреждение содержит последние 800 символов вывода процесса. Ошибка запуска одной стратегии даёт `SCAN_STRATEGY_FAILED`. Эта ошибка не удаляет результаты предыдущих стратегий и не останавливает маршрут. Если 5 стратегий подряд не запускаются, сканирование останавливается с ошибкой `SCAN_STRATEGIES_DO_NOT_START`. Обычно это значит, что winws2 или его драйвер не может запуститься.

## 10. Предварительная проверка и `curl`

`CurlBlockCheckProbeRunner` сначала выясняет:

- доступен ли `curl.exe`;
- поддерживает ли curl `--tls-max`;
- поддерживает ли curl TLS 1.3;
- поддерживает ли curl HTTP/3.

Если сборка curl не может выполнить выбранную проверку, дополнение возвращает ошибку предварительной проверки до того, как изменит состояние компонентов. Ошибки: `CURL_NOT_AVAILABLE`, `CURL_TLS_MAX_UNSUPPORTED`, `CURL_TLS13_UNSUPPORTED` и `CURL_HTTP3_UNSUPPORTED`.

Каждый запрос использует `--connect-timeout`, `--max-time`, `--output NUL`, машиночитаемый `--write-out`, отдельный User-Agent и фиксированный `-4` или `-6`. Запросы HTTP, TLS 1.2 и TLS 1.3 используют `--http1.1`. Запросы TLS по умолчанию используют полный GET, а не HEAD. Запросы QUIC по умолчанию используют HEAD и `--http3-only`. `TlsAuto` не принуждает HTTP/1.1 или версию TLS. Поэтому он ближе к обычному HTTPS-клиенту, но не является браузером.

Попытка успешна, когда `curl` завершается с кодом 0 и возвращает ненулевой HTTP-статус. Для протокола `Http` ответ также не должен выглядеть как заглушка провайдера. Статус 400, статус 451 и перенаправление (3xx) на другой сайт считаются неудачами. Статус 400 даёт `http-400-possible-fake-leak`. Остальные ответы-заглушки дают `http-<status>`.

Стабильные коды неудач включают:

- `curl-start-failed`;
- `proxy-resolution-failed`;
- `dns-resolution-failed`;
- `connection-failed`;
- `timeout`;
- `tls-handshake-failed`;
- `certificate-validation-failed`;
- `curl-feature-unsupported`;
- `http-status-missing`;
- `curl-exit-N`.

Отчёт хранит число попыток, число успехов, долю успехов, медианный TTFB, TTFB p95, HTTP-статусы и коды неудач.

## 11. Базовая проверка

До запуска Zapret2 дополнение проверяет каждую цель. Оно использует то же число запросов, тот же протокол, URL и версию IP.

У базовой проверки три функции:

1. Она не даёт подбирать обход для маршрута, который работает без Zapret2.
2. Она даёт точку отсчёта для кандидата best-effort.
3. Она удаляет цели, которые системный DNS-резолвер не может разрешить.

Если все попытки для цели завершаются с `dns-resolution-failed`, дополнение добавляет цель в `IgnoredTargetIds`. Синтез и отчёт не используют эту цель, а в проблемы добавляется `DNS_TARGETS_IGNORED`. Если не разрешается ни одна цель, дополнение возвращает `NO_RESOLVABLE_TARGETS`.

Дополнение пропускает маршрут как доступный, только когда все проверки его атомарной группы достигают порога режима. Сообщение `NO_BYPASS_REQUIRED` относится только к тем транспортным маршрутам, которые дополнение проверило. Оно не доказывает, что браузер показывает страницу, что HTTPS после перенаправления с HTTP доступен или что другая версия IP работает.

## 12. Сканирование стратегий

Сканирование использует только стратегии выбранного уровня, которые применимы ко всем целям атомарной группы. Порядок прогрессивный: сначала идут низкие уровни. Внутри уровня сканирование берёт по одной стратегии из каждого семейства по очереди, и более дешёвые семейства идут первыми.

Один запуск Zapret2 обслуживает одну комбинацию стратегии и атомарной группы. Пока процесс работает, сканирование проверяет все цели группы со всеми повторами. Это важно для TLS 1.2, TLS 1.3 и для списков: стратегия успешна для группы, только если она достигает порога на каждой цели.

Данные прогресса содержат:

- фазу;
- завершённые и общее число заданий стратегий;
- текущий URL;
- отдельное описание подключения;
- текущую стратегию;
- номер попытки;
- успешные и неудачные запросы;
- число успешных технически разных стратегий.

При ранней остановке маршрут останавливается после того, как сканирование находит нужное число разных успешных планов. При полном тесте сканирование пробует все применимые стратегии выбранного уровня.

Ошибки одного запроса, генерации аргументов, запуска процесса или остановки процесса становятся доказательствами и проблемами. Сканирование сохраняет собранные элементы `ProbeResult`.

## 13. Автоматический синтез пресета

### 13.1. Доказательства

`ProbeResultAnalyzer` собирает попытки для каждой стратегии и цели в `CandidateEvaluation`. Кандидат проходит строгий порог только при достаточном числе попыток и нужной доле успехов.

### 13.2. Фильтр Парето

`ParetoReducer` удаляет кандидата, если другой кандидат:

- покрывает все цели, которые покрывает первый кандидат (кандидат без строгого покрытия остаётся);
- имеет не меньшую минимальную стабильность;
- не медленнее по худшему p95;
- не имеет более высокой базовой стоимости;
- строго лучше хотя бы по одному критерию.

Эквивалентные планы детерминированно сводятся к одному ID.

### 13.3. Строгое покрытие

`CoverageOptimizer` решает жадную задачу покрытия для атомарных групп. Оценка — это ценность нового покрытия, делённая на эффективную стоимость. Эффективная стоимость учитывает:

- базовую сложность стратегии;
- задержку p95;
- штраф за нестабильность;
- веса режима Speed, Balanced или Stability.

Если две оценки равны, оптимизатор сравнивает число маршрутов, минимальную долю успехов, p95 и стабильный ID.

### 13.4. Best effort

Если ни одна стратегия не достигает строгого порога, `BestEffortCoverageOptimizer` может выбрать «лучшую из плохих» стратегию. Он делает это, только если стратегия даёт лучший результат, чем базовая проверка. Приоритет такой:

1. число целей, которые проходят строгий порог;
2. число целей хотя бы с одним успехом;
3. общее число успешных запросов;
4. общая доля успехов;
5. p95;
6. базовая стоимость и ID.

Результат best-effort не выглядит как проверенный результат. Отчёт и профиль получают `IsBestEffort`, а в проблемы добавляется `BEST_EFFORT_CONFIG`. Если ни одна стратегия не улучшает базовую проверку, дополнение не создаёт пресет и возвращает `NO_EFFECTIVE_STRATEGY`.

### 13.5. Профили и запасные варианты

`ProfilePlanner` объединяет назначения, только если совпадают такие элементы:

- нормализованный план стратегии;
- версия IP;
- транспорт;
- порт;
- протокол L7;
- флаг best-effort.

Домены из прямого ввода попадают в `--hostlist-domains`. Цели из файлов сохраняют свои исходные пути и попадают в `--hostlist`. Более конкретные профили доменов идут перед общими профилями.

`CircularFallbackPlanner` добавляет только стратегии, которые:

- успешны на всех целях профиля;
- поддерживают circular;
- не требуют pre-host;
- имеют другую фактическую сигнатуру.

Основная стратегия профиля также должна поддерживать circular и не должна требовать pre-host. Несколько стратегий, которые работают по отдельности, не всегда работают вместе. Поэтому после синтеза дополнение всегда проверяет командную строку всего пресета.

## 14. Аргументы Zapret2

`Zapret2ConfigWriter` создаёт одну командную строку.

Перед профилями модуль записи добавляет общие фильтры WinDivert и библиотеки:

- `--wf-tcp-out` и `--wf-udp-out`;
- входящие порты только для стратегии circular или стратегии со входящим трафиком;
- общие блобы;
- `--lua-init=@lua/zapret-lib.lua`;
- `--lua-init=@lua/zapret-antidpi.lua`;
- `--lua-init=@lua/zapret-auto.lua`, если профиль использует circular.

`--new` разделяет профили. Каждый профиль получает явные значения для:

- `--filter-l3`;
- `--filter-tcp` или `--filter-udp`;
- `--filter-l7`;
- `--hostlist` или `--hostlist-domains`;
- `--name`.

Модуль записи всегда заключает путь каждого `--hostlist` в двойные кавычки, даже если в пути нет пробелов. Кавычки в значении он экранирует.

Для каждого действия Lua модуль записи снова добавляет «липкие» фильтры `--payload`, `--in-range` и `--out-range`. Строка становится длиннее, но ни одно действие не может случайно получить состояние предыдущего действия или профиля.

Профиль circular получает один общий экземпляр `circular`, пронумерованные действия `strategy=N` и `final` на последней запасной стратегии, если параметры модуля записи это разрешают.

## 15. Проверка и исправление готового пресета

`BlockCheckPresetValidationService` запускает всю синтезированную командную строку и снова проверяет все активные цели.

Если кандидат не проходит проверку, сервис выполняет такие шаги:

1. Находит профили и фактические сигнатуры стратегий для неудачных целей.
2. Удаляет эти пары стратегии и маршрута из исходных доказательств.
3. Снова выполняет синтез.
4. Полностью проверяет нового кандидата.

Режим ограничивает число итераций исправления. Возможные итоговые проблемы: `PRESET_VALIDATION_FAILED`, `PRESET_REPAIR_LIMIT_REACHED`, `PRESET_REPAIR_STALLED` и `PRESET_REPAIR_NO_CANDIDATE`. Успешное исправление добавляет `PRESET_REPAIRED`.

Сбой инфраструктуры не доказывает, что стратегия не работает. Сервис записывает его отдельно.

## 16. Обработка отмены и сбоев

Ручная остановка переводит сеанс в `Canceling` и отменяет текущий запрос. Затем сервис сканирования:

- останавливает временный процесс Zapret2;
- сохраняет завершённые базовые проверки и проверки стратегий;
- добавляет `RUN_CANCELED` или `SCAN_CANCELED`;
- пытается выполнить синтез по имеющимся данным;
- создаёт частичный отчёт.

Если отмена происходит во время проверки пресета, отчёт содержит результаты сканирования и первого синтезированного кандидата. Отчёт не содержит попытки проверки пресета и кандидатов исправления. `WasCanceled` не допускает полного успеха.

Необработанное исключение вне обычных пределов показывается как ошибка операции. Ошибка автоматического сохранения в историю не удаляет отчёт из памяти. UI показывает эту ошибку отдельно.

## 17. Оценки времени

### 17.1. До запуска

`BlockCheckMaximumDurationEstimator` рассчитывает консервативный предел. Он предполагает, что 80% запросов завершаются неудачей. Неудачный запрос занимает весь `RequestTimeoutSeconds`.

Оценка включает:

- все запросы базовой проверки;
- применимые задания стратегий;
- число повторов для каждой цели;
- паузу после запуска каждого процесса;
- первую проверку пресета;
- максимальное число проверок исправления.

При ранней остановке оценка предполагает, что успешна одна стратегия из пяти. Поэтому оценка включает число заданий, которое ожидается до предела успешных стратегий. С `TestAllStrategies` оценка включает весь выбранный уровень.

### 17.2. Во время запуска

ETA текущего этапа использует экспоненциальное скользящее среднее с `alpha = 0.2`. UI также оценивает общее оставшееся время. Во время базовой проверки у дополнения недостаточно данных. Поэтому UI показывает «Расчёт после первых завершённых стратегий…», а не выдуманное число.

Счётчики успехов, ошибок, завершённых запросов и найденных стратегий меняются после каждой попытки.

## 18. Отчёт

Версия схемы JSON — `2`. `BlockCheckReport` содержит:

- время UTC и версию каталога;
- режим, `Success`, `WasCanceled` и `IsBestEffort`;
- нормализованные цели и маршруты выполнения;
- проверки базовой линии, стратегий и проверки пресета;
- итоговые профили и их область действия;
- ID основных и запасных стратегий;
- кандидатов проверки;
- проблемы;
- готовую строку `PresetArguments`.

Отчёт записывает неопределённые медиану или p95 как `null`. Поэтому JSON не содержит `Infinity` или `NaN`.

Доступны такие форматы:

- экспорт JSON для дальнейшей работы в приложении;
- текстовый диагностический отчёт;
- файл TXT с аргументами пресета.

Экспорт TXT с аргументами требует успешного или явно помеченного best-effort отчёта с непустой строкой.

## 19. Импорт отчёта

`BlockCheckReportImportService` читает файл как строгий UTF-8. Он определяет формат автоматически: текст, который начинается с `{`, — это JSON, остальной текст — текстовый отчёт. Сервис отклоняет пустой файл и файл больше 64 МиБ.

Сервис проверяет версию схемы (только `2`), коллекции, значения enum, ID, ссылки на цели и количество элементов:

| Элемент | Предел |
|---|---:|
| `Targets` | 20 000 |
| `Probes` | 200 000 |
| `Profiles` | 20 000 |
| `AttemptCount` одной записи проверки | 0–1 000 |

Сервис также проверяет `PresetArguments` через `ConfigShareService.EnsureNoOutsideWrites`. Трей запускает пресет из отчёта с правами администратора. Поэтому сервис отклоняет отчёт с параметрами, которые записывают файлы: `--debug=@…`, `--wf-save`, `--hostlist-auto` и `--hostlist-auto-debug`. Синтез никогда не записывает эти параметры.

Во время импорта сервис:

- загружает текущий каталог;
- восстанавливает цели и проверки;
- связывает профили со стратегиями по ID. Профиль с неизвестной основной стратегией не восстанавливается;
- заново создаёт попытки по сохранённым счётчикам. Каждая успешная попытка получает медианное время;
- создаёт `BlockCheckResultSession` для ручной работы;
- добавляет предупреждения об отсутствующих файлах списков и неизвестных стратегиях.

Другая версия каталога не мешает просмотру. Но пользователь не может редактировать или тестировать неизвестную стратегию.

Текстовый отчёт содержит меньше структурированных данных. Его парсер определяет возможную область действия по существующим спискам сайтов. Он не назначает отсутствующий список всем целям, потому что это дало бы ложную точность.

## 20. Последние подборы и Магазин

История находится в этой папке:

```text
Store/Items/BlockCheck2
```

Дополнение не переносит и не читает старую тестовую папку `Reports/BlockCheck2`.

Имя файла содержит время UTC, режим, статус и короткий GUID. История хранит не более 50 отчётов JSON. После успешной записи нового отчёта сервис удаляет более старые отчёты.

Элемент Магазина:

| Поле | Значение |
|---|---|
| `Id` | `BlockCheck2` |
| `Name` / `ShortName` | Локализованная строка `RecentBlockCheck2Selections` |
| `Type` | `CDPIUIUpdateItem` |
| `VersionControlType` | `local` |
| `Developer` | `CDPIUI` |

`DatabaseInitializationService.QuickRestore` вызывает `RegisterOnFirstLaunch`. После первой успешной регистрации сервис задаёт `BLOCKCHECK/historyStoreItemRegistrationCompleted=true`. Поэтому следующий запуск не добавляет элемент снова после того, как пользователь удалил его в настройках памяти Магазина.

Перед сохранением нового отчёта `EnsureRegistered` при необходимости создаёт папку и запись Магазина. Поэтому история, которую пользователь удалил, остаётся удалённой, пока BlockCheck2 не создаст новые данные.

Удаление элемента Магазина использует обычный `StoreHelper.RemoveItem`. Он удаляет папку отчётов и запись в базе данных Магазина.

Страница последних подборов позволяет пользователю:

- открыть запись в окне результата;
- открыть отчёт JSON или TXT из файла;
- показать файл в Проводнике;
- удалить один отчёт после подтверждения;
- открыть папку;
- обновить список.

`BlockCheck2ResultWindow` — отдельное окно с фоном Mica Alt. У него есть общий MenuBar, строка состояния и центр компактных уведомлений. Строки окна:

### 22.1. Результат подбора

Страница показывает стратегии по сайтам. `SemanticZoom` переключает между полным списком и обзором групп. Пользователь может искать, фильтровать по успешным, частичным и неудачным результатам и сортировать по результату, сайту и времени ответа.

Строка показывает фактическое имя стратегии, URL, отдельные данные подключения, число успехов, долю успехов, время ответа, HTTP-статус, код неудачи и флаг, если пресет использует эту стратегию.

Символ предупреждения означает, что стратегия прошла текущую строку, но дополнение не доказало её работу для всей области выполнения, например для другой версии TLS. ToolTip объясняет символ.

Пользователь может:

- протестировать стратегию отдельно с временным профилем и `curl`;
- запустить её как временный компонент для ручной проверки;
- добавить её для текущего сайта;
- добавить её для связанного списка сайтов;
- скопировать её как действия или как полную командную строку тестового профиля.

### 22.2. Сборка пресета

Сборщик показывает автоматические профили как назначения. Пользователь может удалять, перемещать или добавлять назначения. Порядок назначений в одной области действия задаёт основную стратегию и циклические запасные варианты.

Ручной сборщик проверяет:

- что стратегия и цель существуют;
- что стратегия применима ко всей области действия;
- поддержку circular;
- что ни один фактический план не дублируется;
- что доказательства есть;
- что все цели области действия проходят порог;
- что области действия не пересекаются.

Сборщик показывает одинаковые предупреждения один раз со счётчиком. Он группирует их по коду, сообщению и объектам. Для `MANUAL_SCOPE_OVERLAP` пользователь может быстро принять предупреждение в сборщике. Это не скрывает ошибки других типов и не меняет назначение.

Предпросмотр командной строки использует `TextControlBox` в общем редакторе с автоматическим форматированием по флагам. Кнопка, которая открывает готовый пресет, находится в области сборщика и в меню действий. Обе открывают одну и ту же страницу обзора.

### 22.3. Диагностика

Раздел показывает проблемы отчёта и полный список проверок. Предупреждения ручного сборщика отделены от диагностики редактора командной строки.

## 23. Черновик и обзор готового пресета

`BlockCheck2PresetDraft` хранит две формы:

- структурированную командную строку из автоматического или ручного сборщика;
- временную экспертную командную строку.

Значение `Origin` — `Automatic`, `Manual` или `ModifiedAutomatic`. Структурированные назначения — источник истины, пока пользователь не включит экспертное редактирование.

На `PresetReviewPage` командная строка по умолчанию доступна только для чтения. Флажок «Разрешить редактирование» после подтверждения включает экспертный режим и панель команд ConfigMaker. Возврат к сборщику после изменения экспертной строки требует подтверждения и удаляет экспертные изменения. Причина: дополнение не может преобразовать произвольный текст обратно в назначения без потери данных.

Панели «Используемые файлы» и «Группы пресета» — часть редактора:

- файлы разделены на группы: списки TXT, библиотеки и payload;
- группы показывают общие фильтры, фильтры профилей и последовательность действий;
- для Zapret2 флаги получают пояснения к их фактическим значениям;
- двойной щелчок по элементу группы переводит редактор к точному вхождению, в том числе для повторяющихся флагов;
- панели меняются при изменении командной строки.

Для файла доступны команды «Открыть», «Показать в папке» и, для отсутствующего файла, «Заменить». Редактор открывает файл TXT в приложении из настроек. Если приложение не задано, открывается `EditSitelistAskApplicationContentDialog`.

Замена отсутствующего файла использует `ConfigImportAutoCorrector`:

- пользователь выбирает автоматическое исправление или файл;
- рекомендацией может быть пустой файл;
- редактор заменяет все вхождения исходного пути, а не только первое;
- дерево файлов и группы меняются после замены.

`ConfigMakerUserControl` получает справку Zapret2 через трей и ConPTY. Поэтому он может использовать и компоненты, которым нужен UAC. Парсер восстанавливает логические строки из управляющих последовательностей терминала, группы справки, продолженные длинные описания и флаги без описания. Неизвестный `--help` не является фатальным, если процесс показывает список параметров.

У редактора есть поиск, замена, масштаб, шрифт, фон, форматирование по флагам, предупреждения и ошибки без отвлекающей анимации, а также временный запуск конфига.

## 24. Сохранение пресета

### 24.1. TXT

Пользователь может сохранить текущую действующую строку как обычный файл TXT. Это не меняет хранилище CDPI UI.

### 24.2. В приложении

Перед сохранением пользователь вводит имя. `BlockCheck2PresetStorageService` выполняет такие шаги:

1. Убеждается, что пресет не пустой и Zapret2 установлен.
2. Находит значения `--hostlist`, `--hostlist-exclude`, `--lua-init` и файловые значения `--blob`.
3. Разрешает абсолютные пути, пути относительно компонента и пути с `$GETCURRENTDIR()`.
4. Сохраняет библиотеки и payload из папки Zapret2 как пути относительно компонента.
5. Копирует внешние списки в `LocalUserStorage/List/BlockCheck2/<storageId>`.
6. Копирует внешние библиотеки и payload в `LocalUserStorage/Bin/BlockCheck2/<storageId>`.
7. Меняет все ссылки на `$GETCURRENTDIR()/List/...` или `$GETCURRENTDIR()/Bin/...`.
8. Создаёт пользовательский JSON `ConfigItem` для Zapret2.
9. Обновляет список конфигов компонента.

Сервис сохраняет русское или другое Unicode-имя пресета как отображаемое имя. ID папки и имя JSON он транслитерирует в ASCII, удаляет небезопасные символы и добавляет время Unix, например `Novyi_preset_1786437896.json`. Имена скопированных файлов он тоже транслитерирует. При совпадении имён добавляется суффикс `_2`, `_3` и так далее.

Если возникает ошибка, сервис удаляет незавершённые папки зависимостей. Исходные пользовательские файлы он не меняет.

## 25. Локализация

Основные строки находятся в этих файлах:

```text
CDPIUI/Strings/ru/Resources.resw
CDPIUI/Strings/en-us/Resources.resw
```

Русскому слову «Пресеты» в английском соответствует «Configs». Новые элементы UI должны получать текст через `l:Uids.Uid` или `ILocalizer`. Не переводите технические ID, коды проблем, ключи отчёта и ID стратегий.

## 26. Тесты

В решении нет отдельного тестового проекта для BlockCheck2. В `CDPIUI.Tests` сейчас нет тестов BlockCheck2. Ядро не использует WinUI или трей. Поэтому тесты могут использовать поддельные реализации `IBlockCheckStrategyRunner`, `IBlockCheckProbeRunner` и `ICommandExecutor`. `CDPIUI.AddOns` открывает `CDPIUI.Tests` доступ к внутренним типам через `InternalsVisibleTo`.

## 27. Известные ограничения

1. Успех curl доказывает работу только для конкретных URL, протокола и версии IP. curl не моделирует ECH, размер ClientHello, откат браузера на HTTP/2 или HTTP/3, подресурсы или JavaScript.
2. Сервис может остаться недоступным в браузере, когда главная страница проходит, но список не включает хосты API, CDN, видео или медиа либо другую версию IP.
3. QUIC есть в модели и каталоге. Стандартный UI скрывает его, пока пользовательский сценарий не завершён и поддержка HTTP/3 в curl не проверена.
4. Голос Discord и произвольный UDP не поддерживаются. Для них нужна другая проверка: захват адреса и порта, управляемый запуск клиента и критерий реального медиа-рукопожатия.
5. Автоматический циклический запасной вариант может зависеть от состояния сети. Поэтому комбинированная проверка обязательна.
6. Текстовый отчёт менее точен, чем JSON. Для дальнейшего редактирования используйте JSON.
7. Импортированный отчёт может ссылаться на отсутствующие локальные файлы или на стратегии удалённой версии каталога. Пользователь может его просмотреть, но пресет нужно исправить.
8. Временные списки для отдельных сайтов остаются, пока на них ссылается доступный результат. Когда пользователь сохраняет пресет, сервис копирует зависимости в постоянное пользовательское хранилище.

## 28. Точки расширения

Чтобы добавить новый транспорт проверок, реализуйте `IBlockCheckProbeRunner` и при необходимости `IBlockCheckProbePreflight`.

Чтобы запускать компонент другим способом, реализуйте `IBlockCheckStrategyRunner`. Ядро дополнения не зависит от WinUI или трея.

Добавляйте новые стратегии в исходный JSON или в расширитель каталога. У каждой стратегии должны быть корректные применимость, уровень, стоимость, упорядоченные действия и флаги circular, pre-host и входящего трафика.

Новый формат отчёта требует более высокой `SchemaVersion`, миграции в `BlockCheckReportImportService` и тестовых примеров. Импорт не должен молча принимать неизвестную схему.

Если вы меняете параметры режимов, держите `Scan.AttemptsPerTarget` и `Validation.AttemptsPerTarget` не меньше `Synthesis.MinimumAttempts`. Иначе предварительная проверка вернёт `RUN_ATTEMPTS_MISMATCH` или `RUN_VALIDATION_ATTEMPTS_MISMATCH` до запуска любого процесса.
